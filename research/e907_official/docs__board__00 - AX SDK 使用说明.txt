1 准备工作 
1.1 编译工具链 
由于本SDK 同时支持arm 和arm64 两种架构，所以我们使用的工具链版本存在两个，一个是
支持arm 架构的gcc version 7.5.0（Linaro GCC 7.5-2019.12）；另一个是支持arm64 架构的gcc 
version 9.2.1 20191025 (GNU Toolchain for the A-profile Architecture 9.2-2019.12 (arm-9.10))，请
您自行至ARM 官方网站下载并安装该版本工具链。 
官方网站的地址： 
https://developer.arm.com/downloads/-/gnu-a 
https://armbian.astra.in.ua/_toolchain/ 
1.1.1 配置安装环境（可选）

操作步骤

测试笔记本电脑Ubuntu 的版本号是：ubuntu-22.04.1

请您以root 用户登录需要配置安装环境的主机。 
步骤2

步骤3

步骤4

步骤5 
执行sudo apt-get install lib32stdc++6 命令后输入y； 
步骤6 
执行sudo apt-get install zlib1g-dev 命令后输入y；

5 根文件系统 
5.1 根文件系统简介 
根文件系统（root Filesystem）是内核启动时挂载（mount）的第一个文件系统，如果系统不能
从指定设备上挂载根文件系统，会导致系统启动出错。系统启动成功之后可以自动或手动挂载
其他文件系统。很明显，一个系统中是可以同时存在不同的文件系统的。 
根文件系统的“根”说明该文件系统是加载其他文件系统的“根”，否则其他的文件系统无法
进行挂载。根文件系统被挂载在根目录“/”之下，在根目录下就存在该文件系统的各个目录和
文件，比如/bin、/sbin、/mnt 等，然后可以将其他文件系统挂载在/mnt 目录下。 
根文件系统包含系统启动时所必须的目录和关键性文件，以及挂载其他文件系统所必须的文件。

5.4.4 UBIFS 
无序区块映像文件系统（Unsorted Block Image File System，UBIFS）是一种用于固态硬盘存储
设备的文件系统，UBIFS 最早在2006 年由IBM 与Nokia 的工程师Thomas Gleixner，Artem 
Bityutskiy 所设计，专门为了解决MTD（Memory Technology Device）设备所遇到的瓶颈。由
于Nand 闪存容量的暴涨，YAFFS 等皆无法再去控制Nand 闪存的空间。UBIFS 透过子系统
UBI 处理与MTD 设备之间的动作。与JFFS2 一样，UBIFS 建构于MTD 设备之上，因而与一
般的块设备不兼容。 
UBIFS 在设计与性能上均较YAFFS2、JFFS2 更适合大容量的NAND FLASH。例如，UBIFS 支
持write-back，其写入的资料会被缓存，直到有必要写入时才写到闪存，大大地降低分散小区
块数量并提高I/O 效率。UBIFS 文件系统目录存储在闪存上，UBIFS 挂载时不需要扫描整个闪
存的资料来重新创建文件目录。 
生成UBIFS 文件系统镜像的命令是： 
mkfs.ubifs -F -q -r /home/usr/fs -m 2048 -e 126976 -c 2047 -o ubifs.img

7.2.4 制作UBIFS 
制作UBIFS 需要两个工具：mkfs.ubifs 和ubinize。 
mkfs.ubifs：用于制作UBIFS image。 
ubinize：根据UBIFS image 制作ubi.img，ubi.img 是通过uboot 直接烧写到NAND Flash 
分区上的。 
Demo 板上的spi nand flash 的型号是xxx，page size 2048 bytes，block size 为64 * 2048 = 131072 
bytes，block count 为1024。制作针对demo 板的UBIFS，执行如下两条命令： 
命令一： 
mkfs.ubifs –F -q -r /home/usr/fs -m 2048 -e 126976 -c 2047 -o ubifs.img 
参数说明： 
-F：使能"white-space-fixup"，如果是通过u-boot 烧写需要使能此功能。 
-r：待制作的文件系统目录。 
-m：最小输入输出大小，一般为page_size，当前spinand 的page_size 为2048byte。 
-e：LEB size 逻辑可擦除块大小，block_size–2*(page_size)=128K-4K=126976。

10.4 平台安全配置 
10.4.1 Firewall 简介 
AX620E 支持通过firewall 对ddr 部分地址段进行保护，例如optee 运行空间中会有使用key 做

SDK 中针对optee 运行空间，使用firewall 做了保护，只允许CPU_SYS 在secure 状态下访问
受保护的mem 区域，具体可参考

！注意： 
AX620E 默认会根据build/projects/AX620E_xxx/project.mak 中配置的
OPTEE_IMAGE_ADDR、OPTEE_RESERVED_SIZE 以及OPTEE_SHMEM_SIZE 对optee 的
运行空间OPTEE_IMAGE_ADDR + OPTEE_RESERVED_SIZE - OPTEE_SHMEM_SIZE – 1 进
行保护； 
 firewall 初始化以及设置保护的region 需要越早越好，需要在安全模式下。

11.2 Linux 内核ramoops 
11.2.1 简介 
ramoops 是采用ram 保存oops 信息的一种技术，该技术使用pstore 机制实现，在内核开关中
用3 个开关控制：PSTORE_CONSOLE 控制是否保存控制台输出，PSTORE_FTRACE 控制是
否保存函数调用序列，PSTORE_RAM 控制是否保存panic/oops 信息。

%t - 添加core 文件生成时的unix 时间 
%h - 添加主机名

13 SDK OS Memory 统计 
13.1 概要说明 
13.1.1 需求背景 
在进行稳定性问题分析时候，内存泄漏问题不太容易分析，在发生内存泄漏的时候不太好分析
那个模块或者那个进程发生了内存泄漏； 
在进行内存统计的时候需要统计某个模块分配的系统内存的空间大小，方便进行优化，以及内
存需求的计算； 
SDK 提供了OS Memory 的统计功能，可以分模块统计每个模块申请的系统内存大小以及申请
内存的次数，简称OS_MEM。 
13.1.2 支持的功能 
 同时支持应用态和内核态的内存统计； 
 能同时统计每个模块对应申请的内存大小和申请次数； 
 针对内核的分配，大小计算支持aligned 操作，aligned 策略和linux 版本保持一致； 
 支持名字为common 的ID，方便给osal 等一些不属于具体模块的内存申请； 
 支持不同统计策略，在小内存的软件中，只是统计申请的次数，不记录每次申请的ID 和
大小，对于大内存统计更加详细，该开关通过/proc 节点来配置，默认是小内存，减少统计
的内存消耗和时间开销； 
 提供显示某个模块内核态内存的大小和mod_id/sub_id 的详细信息。

13.1.3 不支持的功能 
 不支持单个模块内核或者用户态申请的内存大于4GB，但是支持内核态和用户态申请的内
存总和大于4GB； 
 不支持没有调用接口的内存统计，例如C++的new/delete、系统的文件cache。 
13.1.4 统计策略 
policy：OS_MEM 进行内存统计的时候的策略，引入是为了os_mem 可以使用不同的场景，目
前支持0-2 3 个policy： 
0：OS_MEM 分配内存可以支持多进程，统计只能统计多进程的次数，不支持统计多进程的大
小； 
1：OS_MEM 可以统计每个模块分配内存的次数，每个模块每次分配的内存大小，在计算最大
分配次数和分配内存大小的时候，只统计当前正在运行的所有进程历史的最大分配次数和分配
大小，不包括已经关闭的进程的内存分配； 
2：OS_MEM 可以统计每个模块分配内存的次数，每个模块每次分配的内存大小，在计算最大
分配次数和分配内存大小的时候，统计从开机到当前所有进程的最大分配次数和分配大小，包
括已经关闭的进程的内存分配； 
policy 可以通过文件节点来配置，默认使用0 plicy（CPU loading 影响最小，内存占用最小），
如果要统计详细信息，可以在所有模块的ko load 之前通过echo 节点进行配置； 
方法如下： 
echo 0 > /proc/ax_proc/os_mem/policy   # 设置policy 为0 
echo 1 > /proc/ax_proc/os_mem/policy  # 设置policy 为1 
echo 2 > /proc/ax_proc/os_mem/policy  # 设置policy 为2
